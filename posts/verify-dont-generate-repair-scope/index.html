Technical Report

Verify, Don't Generate: Recovering Dropped Recall in Insurance Repair Scope Prediction

A retrieve-then-verify architecture recovers the recall that retrieve-then-generate drops
Lodgicl Engagement August 2026 Synthetic Benchmark v1
Abstract

Insurance repair scoping predicts a set of line items from a damage description. Each line item is a {room, trade, item} triple from a closed catalog. The current system retrieves the 20 most similar historical assessments. It then prompts an LLM to generate line items from that context. Retrieval accuracy is 85–90%, but recall stays at ~0.50. With perfect retrieval, recall only increases to ~0.65. The LLM does not re-emit items it receives. This is an architectural failure. LLMs systematically under-produce when they generate sets in one pass. We built a synthetic benchmark with 19 rooms, 20 trades, 90 items, and 2,000 jobs. We show that a retrieve-then-verify architecture lifts recall to 0.90. This architecture uses only a logistic regression verifier. The retrieved candidate pool already contains 99.7% of correct answers. The task is selection, not generation.

1

Background

An insurance assessor inspects property damage and writes a free-text description. From this description, a repair scope of works must be produced. A scope of works is a set of costed line items. Each line item is a triple: a room or area, a trade, and a catalog item. The scope is priced against a schedule of rates.

Lodgicl automates this task. Their system embeds the damage description and retrieves the 20 most similar historical assessments by cosine similarity. It puts them in an LLM prompt. The LLM generates the line items. The system then maps these items to catalog IDs.

Retrieval works well. P50 accuracy is 0.90. The correct historical context is almost always available. The problem occurs in the next step. The LLM generation step drops approximately half the items it receives.

2

Problem Diagnosis

The production metrics show the problem:

MetricMeanP50
Retrieval accuracy0.840.90
Precision0.720.67
Recall0.500.50

With oracle retrieval, recall only reaches ~0.65. Oracle retrieval puts the exactly correct historical items in context. The model does not re-emit items it was given. This failure has four causes.

Set-generation incompleteness. LLMs that generate a set in one pass stop early. They under-produce. In the closest analog (ICD medical coding), prompted generation scores ~18% micro-F1. Per-label verification reaches ~73% on the same data.

Lost-in-the-middle effect. With 20 retrieved assessments in context, the model ignores items in the middle of the prompt. The literature shows a >30% positional accuracy difference.

Near-miss variant errors. Free generation must reproduce exact catalog strings. Errors such as "2m3 skip" against "3m3 skip" show that a generator does a selector's job.

Label inconsistency ceiling. Two assessors scope the same damage differently. Our benchmark shows that 15% label noise causes 3–5 recall points of loss. Part of the gap is not measurable.

Key Insight

The candidate pool already contains almost every correct answer. The generation step discards ~40% of what retrieval found. Any architecture that verifies each candidate, instead of asking the LLM to re-generate, converts retrieval quality directly into recall.

Methodology

No public dataset matches this task. Real corpora (Xactimate estimates, SOR-coded repair logs) are proprietary. We built a synthetic benchmark to isolate the architectural question.

Vocabulary. A closed catalog of 19 rooms and areas, 20 trades, and 90 line items. The catalog uses Australian insurance-repair terminology.

Scenarios. 10 peril types with causal item chains. The descriptions state only observable symptoms. Waste removal, supervision, drying, and seal-coats are implied. They do not appear in the text. This matches real assessor behavior.

Data generation. 2,000 jobs at approximately 10 items per job. The split is 70/15/15 (train/dev/test). A label-noise flag adds assessor inconsistency. This lets us study the measurement ceiling.

Retrieval. TF-IDF with bigrams over training descriptions. This is a cheap stand-in for the production embedding retrieval. It is sufficient to test the architectural question.

Metrics. Set precision, recall, and F1 at three levels: exact triple (room + trade + item), item only, and coarse (room + trade). We report micro-averaged and per-job percentile (P50, P90) values.

Systems tested:

Candidate pool (oracle). Predict every triple from the top-20 neighbours. This measures the recall ceiling of retrieval.

kNN union vote. Keep a candidate if it appears in more than v of the top-20 neighbours. We tune v on the dev set. This uses no learned model.

Retrieve-then-rank. A logistic regression verifier scores each candidate on seven features: vote fraction, max and mean similarity, global prior, and lexical overlap. We tune the threshold on the dev set. This is the simplest learned version of the verify architecture.

The candidate pool contains 99.7% of correct triples. Retrieval is solved. The architectural question is how much of that pool a system recovers.

A kNN vote with no model reaches 0.80 recall. The simplest learned verifier reaches 0.90. The production generate-from-context architecture yields ~0.50 recall on the same type of retrieved input.

The recall-oriented verifier has a P10 of 0.75. This means that even the worst-performing 10% of jobs recover at least three quarters of their items. Label noise costs 2–5 recall points. This confirms that part of any real-world recall gap is a measurement ceiling, not model error.

5

Domain Evidence

The retrieve-then-verify pattern is the established solution in every analogous domain.

Medical coding (ICD). State-of-the-art systems use per-label attention. Each code asks "does the text support me?" LLM approaches that use binary verification outperform prompted generation by 100% to 6%.

Extreme multi-label classification. Amazon PECOS and AttentionXML use two stages. First, they shortlist candidates. Then, they score every (input, label) pair with a trained ranker.

Auto insurance estimation. CCC and Tractable use computer vision to classify damage. They then apply deterministic rules to assemble the operations list. No production system generates line items with free-form generation.

6

Strategies

These strategies are ranked by impact-to-effort ratio. They compose with each other.

  1. Enumerate and verify. Collect the candidate pool from retrieved assessments. Ask the LLM yes/no per candidate with one-line evidence. The recall ceiling becomes the pool ceiling (~0.997). Effort: days.
  2. Self-consistency union. Sample the generator 3–5 times at temperature > 0. Union items that appear in 2 or more samples. This typically adds 10–20 recall points. Effort: days.
  3. ID-grounded selection. Output only IDs from the candidate list. Use structured output, not free text. Apply deterministic post-rules for catalog variants. Effort: days to weeks.
  4. Co-occurrence bundle expansion. Mine association rules from historical scopes. Apply them as deterministic expansion after the model's output. Effort: weeks.
  5. Situation classification with routed context. Classify the peril type first. Route to a scenario template that seeds the checklist. Effort: weeks.
  6. Trained verifier. Replace the LLM verifier with a cross-encoder. Train it on historical assessments with hard negatives. Our benchmark shows logistic regression already reaches 0.90. A cross-encoder on real data is the proven end state. Effort: months.
  7. Data levers (parallel). Enrich catalog items with assessor synonyms. Capture assessor rationale. Run a label-consistency audit. Score at three levels so near-misses are visible.
7

Limitations

This benchmark is synthetic. Descriptions come from scenario templates. Retrieval is easier than in production. Do not use absolute numbers as production forecasts. Use them as an architecture comparison.

The Lodgicl production number (~0.50 recall) is reported by their team on their data. It is included only for shape comparison. It was not measured on the same test set.

8

Validation Plan

Week 1. Re-run the oracle experiment with strategy S1 on Lodgicl's data. If recall increases from ~0.65 toward ~0.95, the diagnosis is confirmed. Then apply S1 on production retrieval, plus S2 and S3. Report at all three scoring levels.

Week 2. Mine co-occurrence rules (S4) from the historical corpus. Measure the marginal recall of bundle expansion. Run a label-consistency audit on a 50-claim sample (S7). Decision gate: if S1–S4 reach a plateau below target, scope S6 with their data volume.
